# Task 3: Анализ архитектуры InsureTech

> **Примечание:** Проблемы инфраструктурного уровня (единая БД, одна зона доступности) уже решены в Task 1 — внедрён Patroni-кластер PostgreSQL с master-slave репликацией и развёртывание в двух зонах доступности с HAProxy. Ниже — проблемы уровня интеграции сервисов, решаемые в Task 3.

## 1. Проблемы и риски текущей архитектуры

### 1.1. Синхронный fan-out к страховым компаниям
`ins-product-aggregator` синхронно опрашивает API всех 5 страховых компаний в рамках одного запроса. Время ответа = latency самой медленной компании. Ошибка в одном API обрывает весь запрос. **Риск:** с 10 компаниями время ответа и вероятность таймаута растут экспоненциально.

### 1.2. Polling вместо событийной модели
`core-app` (каждые 15 мин) и `ins-comp-settlement` (раз в сутки) опрашивают `ins-product-aggregator` через REST. Локальные реплики устаревают. Нагрузка создаётся даже при отсутствии изменений. **Риск:** с 10 компаниями объём данных вырастет вдвое — циклы опроса удлинятся, расхождения реплик усилятся.

### 1.3. Tight coupling между core-app и ins-comp-settlement
`ins-comp-settlement` раз в сутки запрашивает у `core-app` все оформленные страховки через REST. Нет гарантии доставки — при сбое данные теряются до следующего дня. **Риск:** с ростом числа страховок nightly batch может не уложиться в окно.

### 1.4. Отсутствие отказоустойчивости для внешних API
Нет Circuit Breaker, Retry, Time Limiter для вызовов API страховых компаний. Ошибка одного API вызывает каскадный отказ. **Риск:** с 10 компаниями количество точек отказа удваивается.

### 1.5. Единая точка отказа — ins-product-aggregator
Единственный источник данных о продуктах. При падении сервиса реплики устаревают. **Риск:** критичность растёт с объёмом обслуживаемых данных.

## 2. Предлагаемые решения

### 2.1. Асинхронная агрегация + кэширование (Redis)
`ins-product-aggregator` самостоятельно собирает данные от страховых компаний по расписанию и кэширует в Redis. REST-эндпоинты отдают данные из кэша мгновенно. Сбой одной компании не влияет на доступность остальных данных.

### 2.2. Event-Streaming (Apache Kafka)
Внедрить Kafka как шину событий:

| Событие | Публикует | Подписчики |
|---------|-----------|------------|
| `ProductUpdated` | `ins-product-aggregator` | `core-app`, `ins-comp-settlement` |
| `PolicyCreated` | `core-app` | `ins-comp-settlement` |

Polling заменяется на push-модель: реплики обновляются немедленно. Сервисы развязаны — `ins-comp-settlement` больше не зависит от доступности `core-app`.

### 2.3. Transactional Outbox для PolicyCreated
**Решение: использовать.** При оформлении страховки `core-app` в одной транзакции БД сохраняет заявку и пишет событие в outbox-таблицу. Debezium (CDC) публикует событие в Kafka. Это гарантирует атомарность и решает проблему dual-write.

### 2.4. Отказоустойчивость для внешних API
Внедрить в `ins-product-aggregator` и `ins-comp-settlement`:
- **Circuit Breaker**  — fail-fast при превышении порога ошибок
- **Retry с exponential backoff** — повторные попытки при временных сбоях
- **Time Limiter** — ограничение времени ожидания ответа
- **Graceful degradation** — исключение проблемной компании из ответа без блокировки всего запроса
